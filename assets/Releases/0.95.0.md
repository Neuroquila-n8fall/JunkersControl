# Cerasmarter 0.95.0 — Beta

Release date: **2026-10-25**. Exact Git tag: **`0.95.0`**, without a `v` prefix. This is a GitHub **prerelease**, not the latest stable release.

This beta improves dynamic-valve cold-weather demand handling, adds deliberately optional forecast assistance, and returns the build to the official ESP32 PlatformIO/Arduino platform. It does not expand the supported hardware: the existing ESP32, compatible Bosch/Junkers Heatronic BM1 and CAN installation requirements still apply. It is not a winter-comfort, gas-savings or heating-system safety certification.

## Highlights

- **Weather support with demand authority.** Normal dynamic-valve control interpolates from an outside-temperature baseline toward the physical boiler maximum according to normalized valve demand, even with zero manual adaptation. `WeatherSupportMaximum` is a **0–100% cap on the weather fraction**, default **60%**, not an overall heating-curve gain. `100` restores the full hybrid weather fraction; `0` removes the weather-weighted baseline. Demand can still raise the request toward the maximum in cold weather. Other operating modes do not acquire this cap.
- **Optional forecast assistance.** `ForecastEnabled` defaults to **false**. `ForecastCoefficient` ranges from **0 to 1**, default **0.5 °C feed per °C expected outside-temperature change**. The available correction is limited to **±2 °C**. Forecast telemetry being available does not mean the correction is applied.
- **Shared calculation and physical bounds.** Production firmware, ESP32 tests and the serial simulator use the same hardware-independent calculation. Fractional precision is retained; half-degree encoding never rounds a heating request above the observed physical boiler maximum. This ceiling applies across heating modes, direct requests and active fail-safe operation. Without a known usable maximum, the request remains **10 °C**. Disabled heating or zero valve demand takes precedence over override, boost and forecast assistance. Bounding a requested setpoint is not a guarantee that measured water temperature never overshoots it.
- **Main-loop-owned runtime controls (breaking HTTP change).** `POST /api/control` and its `/api/control/queued` alias share one handler that no longer changes heating state from the async web task. A document whose present recognized fields are all valid is queued with **202**, not confirmation of completed application or persistence; read `GET /api/runtime` for the applied state. **The previous `200` response with the runtime document is gone.** A malformed or out-of-range recognized field rejects the entire document with **400** without replacing pending controls or forecasts; requests without a recognized control also return **400**, and setup mode returns **503**. One pending normalized document is held; a newer valid document replaces it rather than merging fields. An ordinal ordering guard prevents older queued HTTP forecast input from overriding newer MQTT input, including submissions sharing a millisecond timestamp.
- **Consistent momentary actions and input guards.** Repeating an enabled boost or fast-heatup command over HTTP, the combined MQTT document or the dedicated MQTT topics no longer restarts the boost countdown or fast-heatup reference; disabling boost clears it. Any finite `FeedMinimum` (0–100 °C) remains a valid curve baseline, with the result limited to 10 °C … reported boiler maximum. With the auxiliary outside reference selected, weather calculation stays off until the first auxiliary temperature arrives after boot; `GET /api/runtime` reports it as `null` until then. Stable MQTT/Home Assistant settings persist through coalesced writes with unchanged clamping; HTTP runtime controls remain temporary. Forecast samples and momentary actions are not persistent settings.
- **Localized dashboard and actual firmware version.** English/German controls and the read-only weather/forecast monitor distinguish fresh samples, reduction permission and available correction. Missing/expired samples and refresh failures do not leave apparently current monitor values. Shared metric rows use DOM text rendering. The system section reads the normalized running firmware version from `GET /api/info`; it does not infer a version from the website bundle.

## Platform and compatibility

Source builds now use pinned **`platformio/espressif32@7.1.3`**, **Arduino 2.0.17** and **C++17**. Portable TCP/Wi-Fi adapters retain bounded network connection attempts. This replaces the previous pioarduino platform choice; use the repository's pinned environment rather than assuming an Arduino 3.x build is equivalent. No new SDK, board family or BM2 support is introduced.

Existing wire keys and MQTT topics are retained. **HTTP integrations that call `POST /api/control` must accept `202` and read `GET /api/runtime` instead of parsing the old `200` runtime body.** MQTT/Home Assistant integrations are unaffected. Complete-image packaging derives application/filesystem offsets from the project partition table, checks capacity, overlap and erased-byte padding, and rejects empty input images.

## Installation assets and upgrade procedure

The default release pipeline packages all three images below. Use images from the same release; do not substitute bootloader or partition images for an application OTA upload.

| Asset | Purpose | Installation |
| --- | --- | --- |
| `firmware.bin` | Application-only upgrade | Upload through firmware OTA on an already provisioned controller with the compatible project partition layout. It does not install a bootloader, partition table or frontend. |
| `littlefs.bin` | Matching web frontend and credential-free configuration template | Upload through the filesystem update interface on the compatible layout. Back up configuration first. |
| `cerasmarter-complete.bin` | First installation or deliberate full recovery: bootloader, partition table, OTA metadata, application and LittleFS | Flash over serial at **`0x0`**. Use for a new board, factory firmware or an unknown/incompatible partition layout. It replaces configuration regions, including NVS and LittleFS. |

1. Download your current `configuration.json` and keep a secure offline backup before flashing. It can contain credentials; do not attach it to public issues or releases. Record installation-specific CAN settings and MQTT/Home Assistant identity.
2. Confirm that component updates target the matching `partitions_custom.csv` layout. Application-only flashing cannot repair an incompatible partition table. See the [installation guide](../../README.md#installation-quick-start) for serial commands and component offsets.
3. On an existing compatible installation, update both the application and matching filesystem when upgrading this frontend. Valid configuration is preserved through the existing NVS backup/restore path for filesystem updates; this is not a substitute for an external backup and does not apply to destructive complete-image recovery or factory reset.
4. A fresh release filesystem contains only the credential-free template, with empty Wi-Fi/MQTT credentials and forecast application disabled. A new controller enters access-point provisioning. Configure or upload your installation's settings and use **Reload Configuration** when required.
5. Hard-refresh the browser after the filesystem update to clear cached scripts and translations. Check **System Status** or `GET /api/info` for the running firmware version `0.95.0`, then verify your actual controller configuration and normal heating operation.

**Trusted LAN only:** there is no built-in HTTP authentication or TLS. Configuration endpoints can expose secrets. Do not expose the controller directly to the internet; restrict access to trusted users and networks. Installing boiler-side wiring remains work for a qualified technician.

## Forecast integration: explicit opt-in, no bundled automation file

The firmware does not fetch weather itself and does not automatically install a Home Assistant producer. The [Home Assistant integration guide](../Examples/HomeAssistant/README.md) describes an existing API/UI-managed installation; **no portable automation JSON file is included**. Configure the producer through Home Assistant's configuration API or UI for your own weather provider, complete relevant room selection, discovered firmware entities and actual heating-command MQTT topic. Do not assume installation-specific entity IDs or replace missing firmware entities with fake helpers.

The required trend is the mean of **three distinct future hourly provider temperatures within the next three hours**, minus the **current temperature from that same provider**. Do not subtract the boiler's outside sensor: provider/sensor location offsets must not become a permanent correction. The firmware computes `clamp(-ForecastCoefficient * change, -2, 2)` from `ForecastTemperatureChange`; an already-computed `ForecastCorrection` is not scaled twice.

For valve-mode warming reductions, **the same fresh sample** must grant `ForecastRoomsSatisfied`. Every relevant room must be available and sufficiently freshly reported; rooms not explicitly off must have numeric current/target temperatures, current at least target, and an explicit idle/off HVAC action. Missing data, deficits, active heating, stale reports or an empty room selection deny reduction permission. Thermostat hysteresis makes this intentionally conservative. Cooling assistance can be positive, but remains bounded. Disabled heating, zero valve demand, override, boost and fail-safe hold do not apply forecasts.

Samples are **volatile**, expire from their local receipt time, and clear on reboot. The documented producer renews a **900-second** sample every ten minutes and on relevant weather/room/setting events. Publish samples with **MQTT retain disabled**: replaying a retained sample would create a new lifetime. `POST /api/forecast` also accepts validated sample submissions with **202**; malformed, conflicting, non-finite or incorrectly typed fields and invalid lifetimes are rejected. See the [API reference](../API.md#get-apiforecast-and-post-apiforecast).

Both the firmware forecast switch and the external producer must be enabled intentionally. Disabling the firmware switch stops application immediately; disabling only the producer leaves a previously received sample eligible until expiry. Stable MQTT/Home Assistant forecast settings persist, but samples never do.

## Scheduling and shutdown boundaries

The documented external Home Assistant policy is **`!seasonLock && (insideWindow || valveDemand)`**. A stop time closes the time-window branch; continuing demand may keep desired operation on. It is not an absolute stop, and hysteretic demand does not require every physical valve to be closed before shutdown. This documents accepted external policy, not a new firmware scheduler or a portable automation installer.

Explicit disablement requests 10 °C immediately. The separate low-setpoint latch has a configurable grace period (general default **300 seconds**); boiler pump afterrun is not a guaranteed fixed delay. Desired-operation helpers, device enablement, feed requests, received operating state, flame and pump are different signals. The offline fail-safe schedule is used during sustained MQTT disconnection, not as a second normal-operation stop clock.

## Verification evidence and limits

Fresh checks ran on the isolated bench ESP32:

| Check | Result |
| --- | --- |
| Temperature calculation, including zero/above-maximum minimum regressions | 30 tests passed |
| Real forecast lifecycle | 9 tests passed |
| Real queued-control validation, out-of-range rejection, momentary transitions and auxiliary validity | 12 tests passed |
| Serial simulator: minimum 0 at −10 °C / 100 % static demand, minimum 40 with 35 °C maximum | 75 / 75 / 35 °C |
| Bench HTTP: `/api/control` 202 queued, out-of-range and empty documents 400, auxiliary `null` before first sample | passed |
| Headed browser control page: fractional settings accepted, cleared optional fields omitted | passed |

The fixed application and filesystem were then installed on the author's production controller by OTA with its backed-up configuration. Afterwards MQTT, CAN outside temperature and boiler maximum, stored settings and the calculated feed request (45 °C before and after) matched the pre-update state. Boost over HTTP and over the dedicated MQTT topic raised the request to the 75 °C maximum, a repeated enable did not restart the countdown, and disable restored the normal request. Home Assistant entities reflected the same state; its forecast producer publishes over MQTT and does not use `/api/control`.

Release filesystem images contain only the credential-free template: Wi-Fi/MQTT credential fields are empty, forecast application defaults off, and weather support defaults to 60%. The published checksum manifest identifies the final downloadable asset bytes.

Earlier feature evidence includes 13 serial temperature/forecast scenarios, isolated-AP HTTP handler checks, forecast API/expiry checks, MQTT persistence/coalescing checks and native Home Assistant template evaluations. Passing calculations, lab endpoints and mild-weather observations do not establish winter comfort, gas savings, weather-provider calibration or universal compatibility with every installation. Forecast reductions have conservative guards; availability alone is not proof of a reduction applied in a live installation.
